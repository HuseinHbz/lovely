## ۲. تست مسیر

### چرا «هر ترکیب گزینه‌ها» ضرب دکارتی نیست

سند خواسته «هر ترکیب گزینه‌ها را طی کند». اگر تحت‌اللفظی گرفته شود، با ۱۹ برگه‌ی سه‌تا‌چهارگزینه‌ای چیزی حدود **۱۰⁹** مسیر می‌شود — نه شدنی است نه معنادار.

معنادار نیست چون موتور **خطی** است. `getNextStageId` فقط `STAGES[index + 1]` را برمی‌گرداند و در کل اسکیما هیچ فیلد `goto`، `branch` یا `nextStage` وجود ندارد. یعنی انتخاب‌ها روی مسیر اثر ندارند و حالت هیچ برگه‌ای به انتخاب برگه‌ی قبل وابسته نیست. پس پوشش کامل یعنی: **هر گزینه‌ی هر برگه دست‌کم یک بار زده شود** — و آن ۹۴ حالت است، نه ۱۰⁹.

این را هم به‌صورت ساختاری چک می‌کنیم (`scripts/test-content.mjs` نبود فیلد انشعاب را می‌سنجد) و هم عملی (تست مرورگر هر گزینه را می‌زند و می‌بیند به برگه‌ی بعد می‌رسد).

### نتیجه

```
✓ هر 94 گزینه به برگه‌ی بعد رسید
✓ هیچ خطای کنسول یا استثنای صفحه نیست
```

۹۴ = ۷۵ گزینه‌ی متنی + تعامل‌های `split` و `find` + برگه‌های صرفاً روایی که فقط دکمه‌ی «برگه‌ی بعد» دارند.

## ۳. تست محتوا — و چرا فهرست نام‌ها هش است

فهرستی که نام‌های واقعی را به‌صورت **متن ساده** نگه دارد، خودش همان چیزی را لو می‌دهد که قرار است جلویش را بگیرد. این مخزن عمومی است، پس چنین فایلی دقیقاً نتیجه‌ی معکوس می‌داد.

راه‌حل: `scripts/test-content.mjs` فقط **هش SHA-256** (۱۶ کاراکتر اول) نگه می‌دارد. هر واژه‌ی متن نرمال (حروف کوچک، حذف ZWNJ، یکسان‌سازی ی/ک) و هش می‌شود و با فهرست مقایسه می‌شود. از روی هش نمی‌شود نام را بازساخت، ولی اگر نامی در محتوا بیاید هشش برابر می‌شود و تست می‌شکند.

**محدودیت صادقانه:** هش فقط **واژه‌ی کامل** را می‌گیرد. برای جایی که نام داخل چیز دیگری چسبیده (ایمیل، شماره، نشانی شبکه‌ی اجتماعی) الگوهای ساختاری جدا چک می‌شوند. برای بازبینی سخت‌گیرانه‌تر می‌شود فایل `.forbidden-names` را محلی ساخت (در `.gitignore` است) که آن‌وقت جست‌وجوی زیررشته‌ای هم انجام می‌شود.

### اثبات اینکه واقعاً می‌گیرد

تستی که همیشه سبز است بی‌ارزش است. با گذاشتن موقت یک نام واقعی، یک ایمیل و یک شماره در `content/stages/p09.ts`:

```
✗ content/stages/p09.ts:4 — واژه‌ی ممنوعه پیدا شد
✗ content/stages/p09.ts:5 — نشانی ایمیل
✗ content/stages/p09.ts:6 — شماره‌ی موبایل ایران
✗ content/stages/p09.ts:6 — شماره‌ی طولانی (احتمال شماره‌ی واقعی)
```

بعد از برگرداندن، دوباره سبز. دامنه‌ی جست‌وجو `content/`, `components/`, `app/`, `lib/` است — یعنی همان «کد، UI یا محتوا» که قاعده ۴ می‌گوید. `deploy/` و `docs/` عمداً بیرون‌اند، چون دامنه‌ی واقعی با تصمیم صریح کارفرما آنجا نوشته شده.

## ۵. تست مرورگر — محدودیت محیطی

سند چهار مرورگر خواسته: Safari iOS، Chrome Android، Firefox، Chrome دسکتاپ.

**در این محیط فقط Chromium نصب است.** `/opt/pw-browsers/` فقط `chromium` و `chromium_headless_shell` دارد و دستور نصب مرورگر در این محیط ممنوع است. پس:

| مرورگر              | وضعیت                                                           |
| ------------------- | --------------------------------------------------------------- |
| Chrome دسکتاپ       | ✅ اجرا شد                                                      |
| Chrome Android      | ⚠️ شبیه‌سازی ویوپورت + `isMobile` + `hasTouch`، نه دستگاه واقعی |
| Safari iOS (WebKit) | ❌ اجرا نشد — موتور نصب نیست                                    |
| Firefox (Gecko)     | ❌ اجرا نشد — موتور نصب نیست                                    |

این را نمی‌شود از اینجا سبز اعلام کرد و نمی‌کنم. چیزی که **می‌شود** گفت: هیچ API مرورگری خارج از خط پایه‌ی امن استفاده نشده. تنها موردی که ارزش بررسی دستی روی Safari را دارد `AudioContext` است که در سافاری با پیشوند `webkitAudioContext` می‌آید — و `lib/sound.ts` هر دو را پوشش داده. صدا هم پیش‌فرض خاموش است، پس حتی اگر جایی کار نکند داستان نمی‌شکند.

**کار باقی‌مانده برای کارفرما:** یک بار باز کردن سایت روی آیفون واقعی قبل از فرستادن لینک.

## ۶. دسترس‌پذیری

`axe-core` روی ۹ صفحه با قواعد `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`:

```
✓ axe — هیچ خطای critical نیست
✓ axe — هیچ خطای serious نیست
✓ با Tab به هر 7 عنصر تعاملی می‌رسیم
✓ حلقه‌ی focus روی همه‌ی عناصر دیده می‌شود
✓ هر تعامل بدون متن، aria-label دارد
```

### دو ایراد واقعی که axe پیدا کرد

**۱. `nested-interactive` روی نقشه — از فاز ۶.** گل‌سر مخفی را داخل `<svg role="img">` گذاشته بودم. `role="img"` یعنی «این یک تصویر واحد است» و محتوایش برای صفحه‌خوان presentational می‌شود؛ پس یک کنترل focusable داخلش هم غیرقابل‌دسترس می‌ماند و هم قاعده را می‌شکند. حالا وقتی نقشه محتوای تعاملی دارد، نقشش `group` می‌شود.

**۲. `color-contrast` روی برگه ۲۷.** برچسب «هوا روشن شد» با `text-kaj/70` روی کاغذ به **۴٫۱۹:۱** می‌رسید — زیر ۴٫۵ لازم برای AA.

مورد دوم یک مشکل بزرگ‌تر را لو داد که بخش بعد توضیحش می‌دهد.

## ۷. نقطه‌ی کور گارد کنتراست

`scripts/contrast.mjs` از فاز ۱ سبز بود و `kaj / mahtab` را **۹٫۲۵:۱** گزارش می‌کرد. ولی UI هیچ‌جا `text-kaj` خام نمی‌نوشت — همه‌جا `text-kaj/70` بود، که Tailwind به همان رنگ با آلفای ۰٫۷ تبدیل می‌کند و روی کاغذ به **۴٫۲۰:۱** می‌رسد.

یعنی **گارد سبز بود و رابط قرمز**، چون گارد فقط رنگ خام را می‌سنجید و چیزی که چشم می‌بیند حاصل ترکیب آلفاست.

axe فقط **یک** مورد را قطعی گزارش کرد (برگه ۲۷)، چون بقیه‌ی همان کلاس روی کارت‌اند و لایه‌ی بافت کاغذ نمی‌گذارد axe پس‌زمینه را تشخیص دهد — آن‌ها زیر `incomplete` می‌رفتند، نه `violations`. ریاضی‌اش ولی همان ۴٫۲۰ بود.

### رفع، دو لایه

۱. **ترکیب آلفا در جدول.** `contrast.mjs` حالا تابع `composite` دارد و ردیف `kaj/80 / mahtab` را می‌سنجد: **۵٫۴۷:۱** ✅
۲. **جست‌وجوی کد.** هر `text-<رنگ>/<عدد>` در `components/` و `app/` پیدا می‌شود و اگر از حد امن پایین‌تر باشد build می‌شکند — حتی اگر کسی یادش نرفته باشد ردیف اضافه کند.

حد امن محاسبه‌شده است نه حدسی:

```
kaj/72 → 4.40  رد
kaj/73 → 4.53  اولین قبولی
kaj/80 → 5.47  چیزی که استفاده می‌کنیم (حاشیه‌ی امن)
```

جست‌وجوی کد دو مورد دیگر را هم گرفت که axe اصلاً ندیده بود، از جمله `text-kaj/45` روی برچسب نشان‌های نگرفته که به **۲٫۶:۱** می‌رسید. حالا تفاوت دو حالت از حاشیه و پس‌زمینه می‌آید، نه از کم‌رنگ کردن متن تا مرز ناخوانایی.

اینکه گارد هنوز واقعاً می‌گیرد هم آزموده شد: با برگرداندن موقت یکی به `/60`، `pnpm contrast` با پیام دقیق شکست.

## ۸. کارایی — و چرا Lighthouse نه

سند «Lighthouse ≥ ۹۰ در Performance و Accessibility» خواسته. Lighthouse در این محیط نصب نیست و نصبش وابستگی سنگینی است که به سرور تولید هم می‌رسید. به‌جایش **خود متریک‌هایی که Lighthouse از رویشان نمره می‌سازد** مستقیم اندازه‌گیری شدند، با `PerformanceObserver` در همان صفحه.

روی **build تولیدی** (نه dev)، ویوپورت iPhone 15:

| متریک   | مقدار                   | آستانه‌ی «good» گوگل |
| ------- | ----------------------- | -------------------- |
| FCP     | **۹۲ms**                | < ۱۸۰۰ms ✅          |
| LCP     | **۳۴۸ms**               | < ۲۵۰۰ms ✅          |
| CLS     | **۰**                   | < ۰٫۱ ✅             |
| payload | **۳۴۳KB** در ۱۶ درخواست | —                    |

> **چرا build تولیدی مهم بود:** همین تست روی سرور توسعه ۳٬۰۸۲KB payload می‌داد. قضاوت کارایی روی حالت dev بی‌معنی است و اگر آن عدد را گزارش می‌کردم گمراه‌کننده بود.
>
> **دو تفاوت با Lighthouse واقعی:** اینجا throttling شبکه و CPU اعمال نشده و نمره‌ی ترکیبی حساب نمی‌شود. پس این اعداد **کف** واقعیت‌اند، نه معادل نمره. برای عدد رسمی باید بعد از استقرار روی دامنه یک بار Lighthouse گرفته شود.

### LCP اول `null` می‌آمد — باگ تست، نه محصول

`performance.getEntriesByType('largest-contentful-paint')` در Chromium آرایه‌ی خالی می‌دهد؛ LCP فقط از راه `PerformanceObserver` با `buffered: true` در دسترس است. تست اصلاح شد.

## ۱۰. یک باگ تست که ارزش ثبت دارد

اولین اجرا `p00 گزینه‌ی 1: پیشروی نکرد` می‌داد. محصول سالم بود: تست روی سرور dev اجرا می‌شد و اولین ناوبری هم‌زمان کامپایل هم می‌کرد، پس کلیک روی دکمه‌ای می‌نشست که هنوز hydrate نشده بود.

رفع درست، `waitForTimeout` بزرگ‌تر نبود — تابع `waitReady` منتظر **ظاهر شدن یک دکمه‌ی فعال** و سپس دو فریم `requestAnimationFrame` می‌ماند. شرط واقعی، نه زمان دلبخواهی.
