# فاز ۸ — استقرار

**وضعیت:** بسته ✅
**پذیرش:** با یک هشدار صادقانه در بخش ۷ — اسکریپت‌ها روی یک VPS واقعی اجرا نشده‌اند، چون این محیط توسعه `apt`، `systemd`، `nginx` و `certbot` ندارد. آنچه **آزموده شده** و آنچه **نشده** در همان بخش تفکیک شده.

---

## ۱. نیازمندی سرور

| مورد       | حداقل                                                        |
| ---------- | ------------------------------------------------------------ |
| سیستم‌عامل | Ubuntu 22.04 یا 24.04 LTS                                    |
| RAM        | ۱ گیگابایت (build کمی بیشتر می‌خواهد؛ با ۵۱۲MB یک swap بساز) |
| دیسک       | **۸ گیگابایت آزاد** — بخش ۱٫۱                                |
| دسترسی     | root یا sudo                                                 |
| شبکه       | پورت ۸۰ و ۴۴۳ باز، و رکورد `A` دامنه به IP سرور              |

دیتابیس لازم نیست. طبق قاعده ۲ چیزی برای ذخیره وجود ندارد.

### ۱.۱ دیسک — اعداد اندازه‌گیری‌شده

نسخه‌ی اول این سند «۳ گیگابایت» نوشته بود. **غلط بود.** تمرین کامل استقرار اندازه‌های واقعی را داد:

| بخش                    | اندازه    |
| ---------------------- | --------- |
| یک ریلیز کامل          | **۶۳۸MB** |
| ↳ از آن `node_modules` | ۴۵۷MB     |
| ↳ از آن `.next`        | ۱۷۷MB     |
| ↳ بقیه (سورس)          | ~۴MB      |

`update.sh` پیش‌فرض **پنج** ریلیز نگه می‌دارد. ولی ضرب ساده‌ی ۵×۶۳۸MB درست نیست: pnpm فایل‌های `node_modules` را از انبار مشترکش **هاردلینک** می‌کند (اندازه‌گیری شد: `links=4` روی یک فایل نمونه)، پس بین ریلیزها فقط یک نسخه روی دیسک است. چیزی که واقعاً به ازای هر ریلیز اضافه می‌شود `.next` است.

برآورد واقع‌بینانه:

```
۴۵۷MB   انبار pnpm (یک بار)
۸۸۵MB   پنج .next
~۲GB    اوبونتو + Node + pm2 + Nginx
────────
~۳٫۵GB  کف مصرف — با ۸GB راحت می‌مانی
```

> هاردلینک فقط داخل **یک فایل‌سیستم** کار می‌کند. اگر `--dir` را روی پارتیشن دیگری غیر از انبار pnpm گذاشتی، هر ریلیز کل ۶۳۸MB را می‌گیرد و باید ۵GB فقط برای ریلیزها حساب کنی. در آن حالت `--keep 3` بده.
>
> با دیسک تنگ: `sudo ./update.sh --keep 2`

## ۲. نصب، گام‌به‌گام

```bash
# ۱. کد را روی سرور بیاور
git clone https://github.com/HuseinHbz/lovely.git /opt/wolf-src
cd /opt/wolf-src

# ۲. نصب
sudo ./scripts/install.sh --domain zahrajim.ir --email you@example.com
```

همین. اسکریپت یازده مرحله را خودش انجام می‌دهد:

| #   | مرحله                                                                                          |
| --- | ---------------------------------------------------------------------------------------------- |
| ۱   | بررسی root، تشخیص Ubuntu، بررسی DNS دامنه                                                      |
| ۲   | نصب Node.js 22 LTS از NodeSource (اگر نبود)، `pnpm`، `pm2`، `nginx`، `openssl`، `rsync`، `ufw` |
| ۳   | ساخت کاربر سیستمی `wolfapp` بدون shell                                                         |
| ۴   | کپی سورس به `releases/<timestamp>/` و `pnpm install` و `pnpm build`                            |
| ۵   | ساخت `.env`، تولید توکن و سکرت                                                                 |
| ۶   | راه‌اندازی `pm2` + `pm2 save` + `pm2 startup`                                                  |
| ۷   | رندر `nginx.conf.template` با دامنه، `nginx -t`، ریلود                                         |
| ۸   | گرفتن گواهی با certbot (مگر `--no-ssl`)                                                        |
| ۹   | `ufw` روی ۲۲، ۸۰، ۴۴۳                                                                          |
| ۱۰  | تایمر روزانه‌ی systemd برای `backup.sh`                                                        |
| ۱۱  | بررسی سلامت روی `https://<domain>/gate`                                                        |

آخر کار **لینک و کد دسترسی چاپ می‌شوند**. تنها باری است که کد روی صفحه می‌آید؛ بعدش فقط داخل `.env` است.

### چیدمان روی دیسک

```
/var/www/wolf-hedgehog/
├── releases/
│   ├── 20260805-120000/     ← ریلیز قدیمی
│   └── 20260805-140000/     ← ریلیز فعلی
├── current -> releases/20260805-140000
└── shared/
    ├── .env                 ← توکن و سکرت؛ ‏۶۰۰، مالک wolfapp
    ├── ecosystem.config.cjs ← رندرشده با مسیر و پورت واقعی
    ├── logs/error.log
    └── source/              ← کلون گیت برای update.sh
```

`current` یک symlink است و همین کل ترفند به‌روزرسانی بدون قطعی است: `update.sh` در پوشه‌ی تازه build می‌کند و فقط اگر موفق بود symlink را جابه‌جا می‌کند.

### فرستادن لینک

```
لینک:      https://zahrajim.ir
کد دسترسی: <چیزی که install.sh چاپ کرد>
```

**این دو را جدا از هم بفرست.** توکن عمداً در URL نیست، چون URL در تاریخچه‌ی مرورگر، دکمه‌ی اشتراک‌گذاری و هدر `Referer` می‌نشیند.

## ۳. به‌روزرسانی

```bash
sudo /var/www/wolf-hedgehog/current/scripts/update.sh --ref main
```

ترتیبش طوری است که سایت زنده هیچ‌وقت در معرض یک build شکسته نباشد:

۱. پشتیبان می‌گیرد.
۲. کد تازه را در `shared/source` می‌آورد.
۳. در یک ریلیز **تازه** نصب و build می‌کند — سایت زنده هنوز روی ریلیز قبلی است.
۴. فقط در صورت موفقیت، symlink را جابه‌جا و `pm2 reload` می‌کند.
۵. بررسی سلامت. اگر شکست خورد، **خودش** symlink را برمی‌گرداند.
۶. پنج ریلیز آخر را نگه می‌دارد.

بازگشت دستی:

```bash
sudo ./scripts/update.sh --rollback
```

## ۴. حذف

```bash
# برنامه و سایت می‌روند؛ پشتیبان‌ها و کاربر می‌مانند
sudo ./scripts/uninstall.sh

# همه‌چیز
sudo ./scripts/uninstall.sh --purge
```

برای تأیید باید **نام دامنه را تایپ کنی**. آخر کار دقیقاً می‌گوید چه چیزی حذف شد و چه چیزی ماند — چون «فکر کردم پاک شده» بدترین حالت ممکن برای این پروژه است.

> `--purge` قاعده‌ی `ufw` پورت ۲۲ را **عمداً** حذف نمی‌کند. حذفش یعنی قطع شدن SSH خودت.

## ۵. کارهای روزمره

| کار                    | دستور                                                       |
| ---------------------- | ----------------------------------------------------------- |
| دیدن کد دسترسی         | `sudo grep ACCESS_TOKEN /var/www/wolf-hedgehog/shared/.env` |
| تغییر تاریخ انقضا      | `.env` را عوض کن، بعد `pm2 restart wolf-hedgehog`           |
| بستن فوری لینک         | `LINK_EXPIRES_AT` را به گذشته ببر + `pm2 restart`           |
| باطل کردن نشست‌های باز | `SESSION_SECRET` را عوض کن + `pm2 restart`                  |
| وضعیت                  | `pm2 status`                                                |
| لاگ خطا                | `pm2 logs wolf-hedgehog --lines 50`                         |
| پشتیبان دستی           | `sudo ./scripts/backup.sh`                                  |

> **ری‌استارت بعد از تغییر `.env` اختیاری نیست.** `middleware.ts` در Edge runtime اجرا می‌شود و اسنپ‌شات محیطش موقع بالا آمدن پروسه گرفته می‌شود؛ بدون ری‌استارت، `/api/verify` مقدار تازه را می‌بیند ولی دروازه مقدار قدیمی را. جزئیات در `docs/05-privacy.md` بخش ۴.

## ۶. رفع اشکال

### سایت بالا نمی‌آید

`install.sh` خودش همین فهرست را موقع شکست چاپ می‌کند:

```bash
pm2 logs wolf-hedgehog --lines 50     # ۱. لاگ برنامه
pm2 status                            # ۲. وضعیت پروسه
curl -I http://127.0.0.1:3000/gate    # ۳. پاسخ مستقیم Next
nginx -t && systemctl status nginx    # ۴. پیکربندی Nginx
tail -50 /var/log/nginx/wolf-hedgehog.error.log
getent ahostsv4 zahrajim.ir           # ۶. DNS
```

اگر گام ۳ جواب داد ولی از بیرون نه، مشکل Nginx یا فایروال است، نه برنامه.

### «پیکربندی ناقص است و سرور بالا نمی‌آید»

`.env` ناقص است. هیچ متغیری مقدار پیش‌فرض ندارد — عمدی، چون سایت خصوصی با توکن پیش‌فرض خصوصی نیست. پیام خودش می‌گوید کدام متغیر کم است و با چه دستوری ساخته می‌شود.

### build می‌شکند با «BUILD BLOCKED»

نگهبان پیش‌نویس. یعنی محتوایی تأییدنشده وارد شده. `pnpm drafts:list` فهرست را می‌دهد.

### certbot شکست می‌خورد

معمولاً DNS هنوز منتشر نشده یا پورت ۸۰ بسته است. `install.sh` در این حالت سایت را روی http بالا نگه می‌دارد و هشدار می‌دهد؛ بعد از درست شدن DNS دوباره اجرایش کن — idempotent است و `.env` را دست نمی‌زند.

### ورود کار نمی‌کند و لاگ Next چیزی ندارد

بلوک `location /api/` در Nginx هر درخواست بدون هدر `Origin` را ۴۰۳ می‌دهد. مرورگرها روی POST هم‌مبدأ این هدر را می‌فرستند، ولی اگر پشت پروکسی دیگری هستی ممکن است حذف شده باشد. با `curl -I` و بدون Origin تست کن.

## ۷. آنچه آزموده شده و آنچه نشده

صادقانه، چون این تفاوت برای کسی که قرار است اجرا کند مهم است.

### آزموده شده ✅

| مورد                                       | نتیجه                                                               |
| ------------------------------------------ | ------------------------------------------------------------------- |
| `shellcheck -S warning` روی هر پنج اسکریپت | تمیز                                                                |
| `bash -n` روی همه                          | بدون خطای نحوی                                                      |
| اعتبارسنجی آرگومان و کدهای خروج            | ۲ برای آرگومان بد، ۳ برای غیر root، ۴ برای لغو تأیید                |
| `backup.sh` روی چیدمان شبیه‌سازی‌شده       | آرشیو شامل `.env` + `content/` + `MANIFEST`، مجوز ۶۰۰               |
| نگه‌داشتن `--keep`                         | با ۶ فایل و `--keep 3` → دقیقاً ۳ ماند                              |
| تأیید تعاملی `uninstall.sh`                | جواب اشتباه → خروج ۴ و **هیچ‌چیز حذف نشد**؛ جواب درست → حذف و گزارش |
| بارگذاری `ecosystem.config.cjs` رندرشده    | `cwd`، `script`، `args` و پورت درست resolve شدند                    |
| مقادیر تولیدی `.env`                       | توکن ۳۲ و سکرت ۶۴ کاراکتر، `assertEnv()` قبول کرد                   |

### تمرین کامل استقرار ✅

بعد از نوشتن اسکریپت‌ها، **همان کارهایی که `install.sh` می‌کند** (منهای بخش‌های root-only) یک بار واقعاً اجرا شد: کپی سورس با همان excludeها، `pnpm install --frozen-lockfile`، ساخت `.env` با همان دستورهای `openssl`، `build` تولیدی، فعال کردن symlink، رندر `ecosystem.config.cjs`، و اجرای سرور دقیقاً از همان مسیری که pm2 اجرا می‌کند.

| بررسی                            | نتیجه                                                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| کپی سورس                         | ۱۷۶ فایل                                                                                                                                               |
| `pnpm install --frozen-lockfile` | موفق                                                                                                                                                   |
| `.env` با مجوز                   | ۶۰۰، symlink به داخل ریلیز                                                                                                                             |
| `build` تولیدی                   | موفق (نگهبان پیش‌نویس و بازبینی حریم خصوصی هم رد شدند)                                                                                                 |
| `script` در ecosystem            | واقعاً روی دیسک بود                                                                                                                                    |
| سرور از `current`                | بالا آمد، `/gate` → **۲۰۰**                                                                                                                            |
| توکن تولیدشده                    | **۲۰۰** · توکن غلط **۴۰۱** · `/story/p13` بدون کوکی **۳۰۷ → /gate**                                                                                    |
| `robots.txt` و `X-Robots-Tag`    | هر دو درست                                                                                                                                             |
| اندازه‌ی `/gate`                 | ۱۱٫۳KB در ۱۴ میلی‌ثانیه                                                                                                                                |
| **سواپ اتمیک**                   | ریلیز دوم ساخته شد، symlink جابه‌جا شد، ری‌استارت از `current`، `/gate` → **۲۰۰**، و `/proc/<pid>/cwd` تأیید کرد پروسه واقعاً از ریلیز دوم اجرا می‌شود |

یعنی خود مکانیزم استقرار — چیدمان ریلیز، symlink، اجرا، و سواپ بدون قطعی — **آزموده شده**. آنچه نشده، فقط بخش‌های root-only زیر است.

### آزموده **نشده** ⚠️

هیچ‌کدام از این‌ها در این محیط شدنی نبود:

- اجرای کامل `install.sh` روی VPS تازه (`apt`، `useradd`، `systemd`، `nginx`، `certbot` نیست)
- `pm2 start/reload/save/startup` واقعی
- گرفتن گواهی با certbot
- سواپ اتمیک `update.sh` و بازگشت خودکارش روی سرور زنده
- قالب Nginx روی Nginx واقعی

**پیشنهاد جدی:** اول روی یک VPS یک‌دلاری یا یک ماشین مجازی محلی با یک زیردامنه‌ی آزمایشی اجرا کن، نه مستقیم روی دامنه‌ی اصلی. اگر چیزی خراب بود، `uninstall.sh --purge` سرور را برمی‌گرداند.

### دو باگ واقعی که همین تست‌های محدود پیدا کردند

**۱. `set -o pipefail` اسکریپت را بی‌صدا می‌کشت.** در `uninstall.sh` و `update.sh` یک `sed` روی فایلی که ممکن است نباشد داخل `$( … | … )` بود. `2>/dev/null` فقط پیام را می‌خورد نه کد خروج را، و `pipefail` شکست `sed` را به کل خط پایپ می‌داد. نتیجه: اجرای دوباره‌ی `uninstall.sh` (که دقیقاً همان چیزی است که idempotent بودن می‌خواهد) **بدون هیچ پیامی با کد ۲ می‌مرد**. رفع با شرط `[[ -f ... ]]` قبل از خواندن.

**۲. گزارش حذف دروغ می‌گفت.** `rm -f` روی فایل ناموجود هم موفق است، پس `uninstall.sh` همیشه ادعا می‌کرد لاگ خطای Nginx را حذف کرده — حتی وقتی اصلاً نبود. برای اسکریپتی که کل ارزشش گزارش دقیق است، این یعنی بی‌ارزش شدن گزارش. حالا قبل از حذف وجود فایل چک می‌شود.
